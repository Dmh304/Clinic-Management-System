UC-01: Register User Account
Primary Actor
Guest
Secondary Actors
System (email verification service)
Trigger
Guest clicks the 'Register' button on the Login/Register screen.
Description
A Guest fills in the registration form with personal details (full name, email, password, phone number, date of birth). The system creates a new Patient account with status = PENDING_VERIFICATION and sends an email verification link to activate the account.
Preconditions
PRE-1: The guest accesses the public Login/Register screen.
PRE-2: The email address provided is not already registered in the system.
Postconditions
POST-1: A new record is created in the users table with role = PATIENT and status = PENDING_VERIFICATION.
POST-2: The patient receives an email with a time-limited activation link.
POST-3: After clicking the link, account status transitions to ACTIVE.
Normal Flow
1. Guest navigates to the Login/Register screen and selects 'Register'.
2. Guest fills in: full name, email, password, confirm password, phone number, date of birth.
3. System validates all required fields and format rules (E1, E2).

5. System sends a verification email containing a one-time activation link (valid 24 hours).
6. Guest opens the email and clicks the activation link.
7. System verifies the token, sets account status = ACTIVE.
8. System redirects the guest to the Login screen with a success message.
Alternative Flows
None
Exceptions
E1 — Email already registered:
System displays 'This email is already registered. Please log in.' Guest is redirected to the Login screen.
 
E2 — Password does not meet policy (BR-01):
System highlights the password field and displays: 'Password must be at least 8 characters, including uppercase, lowercase, and a digit.' Guest corrects and resubmits.
 
E3 — Activation link expired:
System displays: 'This activation link has expired. Request a new one?' Guest may request a fresh link.
Priority
Must Have
Frequency of Use
Low; primarily during initial patient onboarding
Business Rules
BR-01 (Password Policy)
Assumptions
Guest has a valid email address. SMTP service is available.

UC-05: Log In
Primary Actor
User, Patient, Receptionist, Lab Technician, Doctor, Pharmacist, Clinic Manager, Admin
Secondary Actors
Google Identity Platform (for OAuth login)
Trigger
User navigates to the Login screen, or the system redirects an unauthenticated request to Login.
Description
Any registered user logs in with email/password or Google OAuth 2.0. The system authenticates credentials, enforces account-lock policy, issues a JWT Access Token and Refresh Token, and redirects the user to their role-specific dashboard.
Preconditions
PRE-1: The account exists in the system with status = ACTIVE.
PRE-2: The user's email has been verified.
Postconditions
POST-1: JWT Access Token (TTL = 60 min) and Refresh Token (TTL = 7 days) are issued.
POST-2: Refresh Token is stored in an HttpOnly cookie.
POST-3: User is redirected to their role dashboard.
POST-4: Login event is recorded in the Audit Log.
Normal Flow
1. User enters email and password on the Login screen.
2. System validates credentials against stored bcrypt hash (E1, E2, E3).
3. System issues JWT Access Token and Refresh Token.
4. System records the login event in the Audit Log.
5. System redirects based on role:
Alternative Flows
ALT-1 — Google OAuth Login (FR-02, Should Have):
1. User clicks 'Sign in with Google'.
2. System redirects to Google Identity Platform.
3. Google authenticates and returns an ID token callback.
4. System validates the token, maps the Google account to a local account (by email).
5. If matched, proceed from normal flow step 3.
6. If no match, system pre-fills registration form and prompts account creation.
Exceptions
E1 — Incorrect password:
System increments login_fail_count. If count = 5 within 30 minutes, account is locked for 30 minutes (BR-02). System displays remaining attempts.
 
E2 — Account locked (BR-02):
System displays: 'Account locked. Try again in X minutes, or contact support.'
 
E3 — Email not verified:
System displays: 'Please verify your email first.' with option to resend the verification link.
Priority
Must Have
Frequency of Use
Very high; every user session
Business Rules
BR-01 (Password Policy), BR-02 (Account Locking)
Assumptions
SMTP available for re-send verification emails. Google OAuth credentials configured for Should Have scope.

UC-06: Log Out
Primary Actor
User, Patient, Receptionist, Lab Technician, Doctor, Pharmacist, Clinic Manager, Admin
Secondary Actors
None
Trigger
Authenticated user clicks the 'Log Out' button from any screen.
Description
The user explicitly terminates their session. The system revokes the Refresh Token, clears the client-side JWT, and redirects to the Login screen.
Preconditions
PRE-1: User has an active authenticated session.
Postconditions
POST-1: Refresh Token is invalidated server-side.
POST-2: HttpOnly Refresh Token cookie is cleared on the client.
POST-3: User is redirected to the Login screen.
POST-4: Logout event is recorded in the Audit Log.
Normal Flow
1. User clicks 'Log Out' from the navigation menu or user-profile dropdown.
2. Client sends the Refresh Token to the logout endpoint.
3. System invalidates the Refresh Token in the database.
4. System clears the HttpOnly cookie on the client.
5. System records the logout event.
6. System redirects the user to the Login screen.
Alternative Flows
ALT-1 — Session expired (Access Token TTL exceeded):
1. Client detects a 401 response on any API call.
2. Client automatically sends the Refresh Token to renew the Access Token.
3. If the Refresh Token is valid, a new Access Token is issued and the action retries.
4. If the Refresh Token is expired or revoked, the system forces logout and redirects to Login.
Exceptions
None
Priority
Must Have
Frequency of Use
Once per session
Business Rules
—
Assumptions
—

UC-07: Reset Forgotten Password
Primary Actor
User
Secondary Actors
System (email service)
Trigger
User clicks 'Forgot Password?' on the Login screen.
Description
A user who has forgotten their password requests a reset. The system sends a one-time reset link to the registered email. The user sets a new compliant password, and all existing sessions are invalidated.
Preconditions
PRE-1: An account with the provided email exists and is ACTIVE.
Postconditions
POST-1: New bcrypt-hashed password replaces the previous one.
POST-2: All existing Refresh Tokens for the account are revoked.
POST-3: Password reset event is logged in the Audit Log.
Normal Flow
1. User clicks 'Forgot Password?' on the Login screen.
2. System displays an email input field.
3. User enters their registered email address.
4. System generates a one-time reset token (valid 15 minutes).
5. System sends a password reset email with the token link.
6. User clicks the link; system validates the token (E2).
7. System displays the New Password form.
8. User enters and confirms the new password.
9. System validates against BR-01 (E3).
10. System hashes and saves the new password.
11. System revokes all existing Refresh Tokens for this account.
12. System shows success message and redirects to Login.
Alternative Flows
None
Exceptions
E1 — Email not found:
System shows a generic response: 'If this email is registered, a reset link has been sent.' (prevents user enumeration)
 
E2 — Reset token expired or invalid:
System displays: 'This link has expired or is invalid. Please request a new one.' User is redirected to the Forgot Password screen.
 
E3 — New password fails policy:
System displays BR-01 requirements inline and prompts the user to retry.
Priority
Must Have
Frequency of Use
Low; occasional per user
Business Rules
BR-01 (Password Policy)
Assumptions
SMTP service is operational. Token TTL = 15 minutes.

Secondary Actors

Trigger
A system event occurs that generates a notification (appointment confirmed, prescription ready, lab result uploaded, invoice issued, etc.).
Description
The system automatically delivers in-app notifications and email alerts to relevant actors when key workflow events occur. Users can view their notification history and mark notifications as read.
Preconditions
PRE-1: Recipient is a registered, ACTIVE user.
PRE-2: A triggering event has occurred within ECMS.
Postconditions
POST-1: Notification record created in the database and linked to the recipient.
POST-2: In-app notification badge count increments in real time.
POST-3: Email notification dispatched if the event qualifies (SMTP available).
Normal Flow

3. System pushes the notification to the user's in-app notification bell via WebSocket.

5. User clicks the notification bell to open the notification panel.
6. System lists notifications (unread and read) with timestamps and brief descriptions.
7. User clicks a notification to navigate to the relevant screen.
8. System marks the notification as read.
Alternative Flows
ALT-1 — Mark all as read:
1. User clicks 'Mark all as read'.
2. System updates all unread notifications for the user to read status and resets the badge count to 0.
Exceptions
E1 — Email delivery failure:
System logs the failed attempt and retries up to 3 times at 5-minute intervals. In-app notification is always delivered regardless of email status.
Priority
Must Have
Frequency of Use
Multiple times per day per active user
Business Rules
—
Assumptions
Real-time delivery uses WebSocket or server-sent events. Email via Gmail SMTP / SendGrid.

The bot may guide the patient on HOW to complete tasks (e.g., how to pay an invoice, where to view a prescription), but does not execute transactions on the patient's behalf, access personal medical or appointment records, or perform appointment booking.
The bot does not provide medical diagnosis; symptom-related questions are answered with general information and a recommendation to consult a doctor.
Preconditions
PRE-1: Patient is authenticated on the Patient Portal.
Postconditions
POST-1: Conversation session is logged.
POST-2: If escalated, a support request notification is sent to the Receptionist.
Normal Flow
1. Patient clicks the chatbot icon to open the chat panel.
2. ECMS-Bot greets the patient and presents quick-reply options: Clinic Info, Services & Pricing, Eye Care FAQs.
3. Patient selects an option or types a free-text query.
4. System classifies the query intent and generates a contextual response from the approved knowledge base.
5. Patient receives the response and may continue the conversation or close the panel.
6. System logs the complete conversation.
Alternative Flows
ALT-1 - Escalate to human Receptionist:
1. Patient asks a query the bot cannot resolve with sufficient confidence (confidence below the configured threshold).
2. Bot responds: 'I'll connect you with our receptionist for further assistance.'
3. System creates a support request notification for the on-duty Receptionist.
 
ALT-2 - Medical or symptom-related query:
1. Patient describes symptoms or asks for a diagnosis.
2. Bot provides general eye-care information only and recommends booking an appointment or consulting a doctor; it does not diagnose (per BR-13).
3. If the patient needs further assistance, the bot escalates to the Receptionist (per ALT-1).
Exceptions
E1 - AI service unavailable:
System displays: 'Our chat assistant is temporarily unavailable. Please call our hotline or send us an email.'
Priority
Should Have
Frequency of Use
Varies; primarily for self-service patient queries
Business Rules
BR-13 (No Medical Diagnosis): The bot must not provide medical diagnosis, treatment decisions, or personalized clinical advice. Symptom-related queries receive general information only, plus a recommendation to book an appointment or consult a doctor.
BR-14 (Knowledge-Base Grounding): The bot answers only from the approved FAQ / clinic-info knowledge base. If no answer meets the configured confidence threshold, it must escalate (ALT-1) instead of generating an unverified answer.
BR-15 (No Transaction or Record Access): The bot may explain how to complete a task but must not execute transactions (e.g., payment) or display personal medical/appointment records; it directs the patient to the relevant Patient Portal function.
Assumptions
Chatbot NLP/NLU backend integrated via REST API.
Bot response confidence threshold configurable by Admin.
Bot answers are generated from a curated FAQ / clinic-info knowledge base; appointment booking and personal record lookups are out of scope for this use case.

5. System applies the action: for Cancel, sets status = CANCELLED and releases the time slot (POST-01a/POST-01b); for Reschedule, updates the appointment time, resets status to PENDING, and notifies the Receptionist role group (POST-02).

EX-04 (at step 2c): No new appointment time is specified. System rejects the request.

Primary Actor
Patient
Secondary Actors
Receptionist (books on behalf of a patient).
Trigger
Patient selects 'Book a Session' from an active service-package subscription on 'My Packages' (UC-40), or selects a single non-medical care service directly from the catalogue.
Description
A Patient with an active service-package subscription (or purchasing a standalone session) schedules a date/time for a wellness/care session (e.g., eye massage, eye meditation). Unlike a doctor appointment, the session does not require a doctor and is later staffed by a Nurse.
Preconditions
PRE-01: The Patient holds an active service-package subscription with at least one remaining session.
PRE-02: The subscription's expired date, if set, has not passed.
Postconditions
POST-01: A care session record is created with status BOOKED, assigned the next sequential session number for that subscription, the chosen date/time, and any optional notes.
POST-02: The subscription's used session count is incremented and the remaining session count is decremented immediately at booking time.
POST-03: If the remaining session count reaches zero, the subscription status is automatically updated to DEPLETED.
POST-04: An in-app notification is sent to the patient confirming the booking.
Normal Flow
1. The Patient opens their care session booking page, optionally pre-filled from a specific subscription.
2. The system lists the Patient's active subscriptions that still have remaining sessions.
3. The Patient selects a subscription, picks a future date and time, and optionally enters notes.
4. The Patient submits the booking request.
5. The system validates that the selected subscription is active, not expired, and has remaining sessions, and that the chosen date and time is in the future.
6. The system creates the care session, deducts one session from the subscription balance, and marks the subscription as DEPLETED if no sessions remain.
7. The system sends a confirmation notification to the patient and confirms the booking.
Alternative Flows
Receptionist books on behalf of a patient. 
A1. The Receptionist opens the booking form for an identified patient's active subscription.
A2. The same validation and session-deduction rules apply; the resulting session and notification are attributed to the patient.
Exceptions
EX-01 (Missing subscription): The system prompts the actor to select a valid subscription before proceeding.
EX-02 (Missing date/time): The system prompts the actor to provide a valid date and time.
EX-03 (Past date/time): The system rejects the booking and informs the actor that the scheduled time must be in the future.
EX-04 (Subscription not active): The system informs the actor that the selected subscription is no longer active.
EX-05 (Subscription expired): The system informs the actor that the subscription has passed its expiry date and marks it as EXPIRED.
EX-06 (No remaining sessions): The system informs the actor that all sessions in the subscription have been used.
EX-07 (Ownership mismatch): The system rejects the request if a Patient attempts to book against a subscription that does not belong to them.
Priority

7. Admin clicks 'Activate Account'.
8. System sets status = ACTIVE and sends a welcome email with temporary credentials.
9. Event is recorded in the Audit Log.
Alternative Flows

1. Admin selects an active account and clicks 'Deactivate'.
2. System sets status = INACTIVE and invalidates all active tokens.
3. Event logged.

ALT-2 — Edit Account Details (Staff only):
1. Admin selects a staff account and modifies: name, role, department.
2. System saves changes and logs the event.

ALT-3 — Search and View Patient Account:
1. Admin switches filter to "Patient" and searches by name, phone number, or patient code.
2. System displays read-only patient account details (profile info, account status, registration date). Admin cannot edit clinical/EMR data from this screen — that remains governed by BR-08.

ALT-4 — Reactivate Patient Account:
1. Admin selects an inactive Patient account and clicks 'Reactivate'.
2. System sets status = ACTIVE.
3. Event logged; optional notification email sent to the patient.
